**Dilution classifier tốt hơn.** FRT giờ không còn tự động kết luận `EXCESSIVE_DILUTION`; engine nói rõ 88.8% share increase còn chưa giải thích, classification là `UNEXPLAINED_SHARE_CHANGE`, `economic_events=[]`, và yêu cầu evidence ESOP/quyền mua/phát hành trước khi hard reject. 

Đây là logic đúng hơn bản trước.

# P0 regression: FRT lại thành `ATTRACTIVE`

Đây là vấn đề lớn nhất của bản này.

Bản trước FRT đã được sửa thành:

```text
AVOID_QUALITY
```

nhưng bản mới overview lại trở về:

```text
FRT
Base IV = 281,549
MOS = +48.2%
Verdict = ATTRACTIVE
```



Trong machine object, FRT vẫn:

```text
quality_score = 54
tier = LOW_QUALITY
cash_quality = 2/10
moat = 6/20
```

nhưng:

```text
verdict_status = ATTRACTIVE
valuation_pill = ATTRACTIVE
```



Việc gỡ `EXCESSIVE_DILUTION` hard reject là đúng. Nhưng nó **không được phép đồng thời gỡ quality floor**.

Invariant nên tách:

```text
raw_valuation_status = ATTRACTIVE

quality_status = LOW_QUALITY

final_status =
    if quality_score < 60:
        AVOID_QUALITY
```

Do đó FRT hợp lý hơn là:

```text
valuation_math = ATTRACTIVE
quality_status = LOW_QUALITY
final_verdict  = AVOID_QUALITY
```

Không nên:

```text
LOW_QUALITY + ATTRACTIVE final verdict
```

# Dilution semantics vẫn còn một inconsistency

FRT đã được classify:

```text
UNEXPLAINED_SHARE_CHANGE
```

và:

```text
economic_events = []
```

nhưng object vẫn ghi:

```text
economic_dilution_5y_pct = 88.8
```



Đây là naming/semantic bug.

Nếu chưa có evidence kinh tế, phải tách:

```text
confirmed_economic_dilution_pct = 0 hoặc null
unexplained_share_change_pct   = 88.8
non_economic_share_change_pct  = 26.8
```

Tôi nghiêng về:

```text
confirmed_economic_dilution_pct = null
```

vì `null = chưa xác định`, còn `0 = xác nhận không có dilution`.

Không nên gọi 88.8% là `economic_dilution` rồi ngay sau đó nói “chưa có evidence để kết luận economic dilution”.

# P0/P1 mới: leverage penalty đang không nhất quán

FRT có:

```text
Net debt = 15.705T
Debt payback = 5.7 years
status = MODERATE
```

nhưng Margin of Safety lại:

```text
leverage_penalty_pct = 0
```

 

Điều này không khớp rule chúng ta đã đặt:

```text
high leverage → +5% đến +10% MOS
```

Tôi parse thêm toàn export và thấy pattern đáng ngờ:

```text
FRT  debt payback 5.7y  → leverage penalty 0
HAG  debt payback 12.3y → leverage penalty 0
BSR  debt payback 3.2y  → leverage penalty 0

nhưng

HAH  debt payback 1.5y STRONG
→ leverage penalty 5
```

Tức penalty hiện **không monotonic với leverage risk**.

Đây cần test invariant:

```text
FORTRESS / net cash
    → 0

STRONG
    → 0

MODERATE 3–5y
    → +5

WEAK / >5y
    → +10
```

Có thể sector override, nhưng override phải explicit và traceable.

```text

    DIVIDEND_HISTORY_LOOKUP

```



Đây là improvement vì giờ biết chính xác record đầu tiên bị lỗi.

Nhưng integrity vẫn chưa được sửa.

Bản trước:

```text
records = 765
```

bản này:

```text
records = 768
```

tức +3 record.

Tôi **không còn kết luận rằng export chắc chắn append activity**, vì +3 có thể đến từ các thao tác khác giữa hai lần export. Cần test cô lập:

```text
count0 = activity.count

export()
count1 = activity.count

export()
count2 = activity.count

assert count0 == count1 == count2
```

Ngoài ra integrity report hiện còn thiếu trường quan trọng:

```text
failure_reason
expected_hash
actual_hash
```

Ví dụ:

```text
failure_reason =
    PREVIOUS_HASH_MISMATCH
    CURRENT_HASH_MISMATCH
    PAYLOAD_MUTATED
    MISSING_HASH
```

Hiện có hash values nhưng chưa biết **vì sao** validator đánh record 73 là broken.
